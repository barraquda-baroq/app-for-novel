# Novel Studio 2.x 仕様書

1.x（端末内だけで動く PWA。`release/1.x` ブランチ）を土台に、端末間のリアルタイム同期と執筆・推敲の機能を加える。
1.x の仕様と設計上の決定は [SPEC.md](SPEC.md) を参照（2.x で変える点はこの文書に書く）。

## 0. 前提と構成

- 完全に個人使用。公開・配布・収益化はしない。
- 端末と形:
  - **Windows**: Web 版（Firebase Hosting に置き、Chrome・Edge の「アプリとしてインストール」で使う）
  - **iPhone / Android**: Capacitor でアプリ化（アプリ ID `jp.barraquda.novelstudio`。2.4、§8）。iPhone は Mac で作って Apple Developer Program の TestFlight（内部テスト）で入れ、Android は Windows か Mac で作って USB で入れる（docs/MOBILE.md）
  - Mac 版は作らない（Mac は iPhone のアプリのビルドにだけ使う）
- クラウド: Firebase プロジェクト `novel-studio-3352e`（Spark 無料プラン）
  - Authentication: Google ログイン
  - Cloud Firestore: スタンダード、リージョン `asia-northeast1`（東京）
  - Hosting: Windows 用 Web 版の配置先

## 1. ユーザーの要件（原文の要約）

1. **同期**: Windows・iOS・Android 相互で、アプリ設定（表示の好み）以外のすべてのデータをリアルタイムに同期する。
2. **各話テキスト書き出し**: 選んだタイトルの採用原稿を1話1ファイルで、保存場所を指定して書き出す。ファイル名は `yyyymmddタイトル名_話数`。
3. **ゴミ箱**: 削除したものを30日保存してから消す。時系列の一覧で、戻すと元の場所に戻る。
4. **保存ボタンと巻き戻し**:
   - 話・幕ブロックの編集は保存ボタンで確定する。保存せずに画面を離れようとしたら、編集が消えることを警告する。
   - 直前の編集（記入・削除など）を戻せる巻き戻しボタン。30手。
5. **戦略領域の追加**:
   - **改稿案**: 案ごとのチェックボックス。実装済み・ボツでチェックすると斜線＋グレーで下へ沈む。文字数制限なし（ワンシーン丸ごとの案もある）。開くと中身を Markdown で表示し、［直す］で書き直す。
   - **推敲案**: Claude 連携による提案。日付順（新しい順）で、種類（誤字脱字・既成表現など）を明示。フラグを立てたものは常に最上位。チェックで消し込める。
6. **セパレート（幕）**:
   - 採用した話を WEB 掲載用に「第n話　題　第x幕」へ分割する。話数は増やさない。
   - 話がフォルダになり、幕ブロックに分かれる。以後の編集は幕ブロックからだけ行う。
   - 幕の画面では話の画面と同じ機能が使え、幕だけの文字数も出る。
   - 幕化した話の採用を外すには、先にセパレートを解除する。
   - 操作: デスクトップは話の一覧で右クリック、スマホは長押し → セパレート／セパレート解除。分割点はクリック／タップでカーソルを置いて Enter か決定ボタン。
7. **文字数**: タイトル全体（採用原稿）・各話・幕。
8. **各話の進捗**: その話がタイトル全体の何割の位置にあるか（転機が物語のどこにあるかを見るため）。
9. **Claude 連携**:
   - ワードサーチ: 作者の癖になっている語・表現、既成表現・手垢のついた表現、誤字脱字・ら抜き・い抜きを洗い出し、推敲案として一覧化する。
   - 批評: 採用原稿でタイトル全体を、執筆者が望む形で批評するためのプロンプトを作り、**作品批評**領域（新設）の批評プロンプト一覧で管理する。実行したプロンプトと批評結果（MD やアーティファクトの URL）を日付ごとに Claude 側から書き込めるようにする。
   - 戦略: 採用原稿をもとに、そのタイトルの今後の戦略（狙うコンテストなど）を決め、戦略領域に反映する。
10. **コピー**: 表示している話・幕ブロックを、話数・幕数・題ごとコピーする（採用・不採用を問わない）。
11. **設定**:
    - 外観3種: ホワイト（白基調・タブはカラフル）／ダーク（黒基調・白地なし・タブはカラフル）／ディープダーク（タブもほぼ黒。職場での内職用）
    - フォント: 各プラットフォームの標準フォント（iOS ならヒラギノ角ゴシック）
12. **その他**:
    - 横書き前提でよい（応募用の縦書きは専用アプリで行う）。段落の一字下げの自動化は不要。
    - ルビ・傍点を振れるようにする。ダッシュ・三点リーダー・全角空白を入れるボタンを付ける。デスクトップは編集画面の一番下、スマホはキーボードの変換候補の上に常に置く。

## 3. 同期の設計

### データの置き場所

- Firestore: 1レコード = 1文書。`users/{uid}/records/{表名}:{レコードID}`。項目は次のとおり（`src/sync/codec.ts`）。
  - `json`: レコードをキーを並べ替えた JSON 文字列にしたもの（端末内の内容とそのまま比べられ、Firestore が扱えない値にも困らない）
  - `hash`: `json` の指紋。送る前に「クラウド側が前回揃えた時から変わっていないか」を確かめるのに使う
  - `updated`: サーバー時刻（書き込み時に付く）。差分の取得に使う
  - `device`: 書いた端末の ID
  - `deleted`: 削除の印（削除は印だけの文書に置き換える。差分の取得で削除も届くようにするため）
  - `chunks`: 1MiB の文書の上限を超えそうな大きなレコード（25万文字を超える JSON）は、分割文書 `{表名}:{id}#{n}` に分けて同じトランザクションで書く
- 端末内: 1.x と同じ IndexedDB（Dexie。v3 で送信待ち `_outbox` と状態 `_meta` を追加）。画面は端末内のデータだけを見る。通信できない間も普通に使える。
- アクセスルール（`firestore.rules`）: 持ち主のアカウントだけが `users/{uid}/records` と、データの形の版 `users/{uid}/meta/app` を読み書きできる（テストでは持ち主の制限を外した `firestore.emu.rules`）。2.3 の Claude 用のコネクタは、持ち主が許可した匿名のアカウントとして読むことと、Claude の10の表（2.3 の6つと、2.5 の相対比較の作品・その分析、2.6 の資料・その記録）に新しく作ることだけができる（§7・§11・§13）。

### 流れ

- **保存（端末内）**: 端末内に保存するたびに、書いたレコードを同じトランザクションで送信待ちに積む。送信待ちには、そのレコードを最後にクラウドと揃えた時の内容（base）を控える（`src/db/persistence.ts`）。
- **送信**: 変更から2秒（続けて編集しても最大10秒）後、または画面を閉じる・裏に回る時に送る。トランザクションの中でクラウド側の `hash` が base の指紋と同じことを確かめてから書く。違っていたら（別の端末が先に書いていたら）書かずに、受信でマージされるのを待って送り直す（`src/sync/engine.ts`）。送る前に、その送信待ちに「返事を受け取るまで、クラウドが base のままか分からない」と印を付ける（書き込みがクラウドに届いたのに、つながりが切れた・アプリを閉じたために返事を受け取れないことがある）。印の付いた送信待ちは、その後に端末内で消した・元に戻して base と同じになっても外さず、次に送る時にクラウドを読んで確かめる（同じなら書かずに終える。クラウドに残っていれば、自分の書き込みの通知を受け取って base を進めてから消す）。外すと、クラウドに残った版が自分の書き込みの通知として戻り、消した幕・稿が生き返るため。
- **受信**: 「前回受け取った `updated` 以降」のリアルタイム購読をする（別々の書き込みが同じ時刻になることがあるので「以降」。同じ時刻の受け取り済みの変更が届き直しても、反映して変わることはない）。購読を始めてから最初にサーバーと揃うまでは、端末の中の控えから作った通知（前の購読で受け取った古い内容のことがある）は使わず、揃った時点の全件を受け取る。届いたレコードは、送信待ちが無ければそのまま反映し、あれば 3者マージ（base・この端末・クラウド）して反映し、base をクラウドの内容に進める。受け取った位置は反映と同じトランザクションで記録する。
- **複数のタブ・ウィンドウ**: 同期は1つの画面だけが受け持つ（Web Locks）。ほかの画面は端末内に保存するだけで、受け持つ画面が送る。ほかの画面の保存も、端末内が先に変わっていれば同期と同じ規則で合わせる。同期の状態は受け持つ画面からほかの画面に知らせる。
- **マージ**（`src/sync/merge.ts`。ほかの画面の保存（`persistence.save`）とクラウドからの反映（`persistence.applyRemote`）の両方で同じ規則）:
  - 項目ごとに、この端末が base から変えた項目だけをクラウド側に重ねる（名前などの短い項目を両方が別々に変えていたら、この端末を優先）。
  - ID の並び（`structure`・`pieceIds`・`versionIds`・設定のフィールドなど）は、この端末の並びを基本に、相手が消したものを除き、相手が足したものを相手の並びでの直前の要素の後ろに入れる。
  - 稿の本文が両方で変わっていたら、クラウド側を正とし、この端末の本文を「第n稿（競合: iPhoneでの編集）」のような新しい稿として話の稿一覧の末尾に足す。
  - 長い文章の項目（メモ・アイデア・設定のエントリの本文、応募計画の概要・規定の備考・提出する梗概・特記事項・結果・方針、あらすじ、全体戦略、章のメモ、推敲メモ）が両方で変わっていたら、クラウド側の文章の後ろに「――――（同期の競合: ○○で同時に書かれた内容）――――」の印を付けてこの端末の文章をつなぐ（その場で両方が見える）。
  - 片方で削除・片方で編集されていたら、削除を優先する。文章を持つもの（稿・メモ・アイデア・設定のエントリ・応募計画）は、編集された内容をゴミ箱に「同期の競合で残した内容」（`reason: 'conflict'`）として残す。
  - 親（タイトル・話・設定項目）が別の端末で削除されたら、この端末にある子も片付ける。子にしか無い文章はゴミ箱に控える（同じ内容がゴミ箱にあれば控えない）。
  - 応募時の原稿の本文（`snapshotTexts`）は、この端末の応募計画が使っている間は、別の端末で消されても残して送り直す。そのため本文の削除は、使っていた応募計画の削除・書き換えの後に送る（足す時は本文を先に送る）。大きな削除・すべて削除が何回かに分かれて届いても、受け取った端末には応募計画の削除が先か同じ通知で届くので、まだ使っていると判断して消したはずの本文を送り直さない。
  - 競合を控えた・文章をつないだ時は、画面で知らせる。
- **幕のまとまりの送信**（2.2。`src/sync/acts.ts` の `groupOutbox`・`src/sync/batch.ts`）: 幕の構成を変えた（分けた・さらに分けた・つないだ・解除した・分けた話を削除した）話の送信待ちがある間は、その話・幕・それらの稿と、まだ送っていないこの操作のゴミ箱の件（戻し先がその話・幕のもの）を1つのまとまりとして、1つのトランザクションで送る。どれか1つでもクラウド側が先に変わっていれば、まとまりは1つも書かない（ほかの端末が、話の幕の並びより先に幕だけを受け取る・幕だけが消える、といった途中の状態を見ないように。Firestore は1回の書き込みを1つの通知で届ける。エミュレーターのテストで確かめている）。受信を待っても解消しない時に直接読み直すのは、書けなかったものだけ。まとまりが1回の上限（400文書・150万字）を超える時は、ゴミ箱の件を先に、それでも超えれば1件ずつ送る（受け取った端末で一時的に途中の状態が見えることがあるが、負けた側が片付ける）。幕の構成を変えていない時（稿の編集・採用など）は今までどおり1件ずつ。まとまりを作るのは端末内の読み出しだけで、クラウドの読み書きは増えない。
- **幕の構成の競合**（2.2。`src/db/persistence.ts` の `applyRemote`・`src/sync/acts.ts`）:
  - 話の幕の並び（`actIds`）がこの端末とクラウドの両方で base から変わっていたら（両方の端末が分けた・さらに分けた・つないだ・解除した）、項目ごとには合わせず、どちらかの構成を丸ごと採る。採るのは、この端末がセパレートを解除し（解除してから分け直した時も）別の端末は解除していない時だけこの端末、それ以外はクラウド（先に送った端末）。共通の履歴が無い時（初めてのログイン）はクラウド。両方が同じ並びに変えていた時（同じ操作をした）は、幕・稿は今までどおり1件ずつ合わせるが、話・幕の採用稿はクラウド（先に送った端末。操作の後の書き換えが採用原稿から抜けないように）にし、この端末の採用稿と本文が違えば知らせる（この端末の稿は稿の一覧に残る）。
  - 話は、幕の並びと採用稿を採った側にし、ほかの項目（題など）は今までどおり項目ごとに合わせる。幕は、採った側の並びに載っている幕だけを採った側の内容で残す（この端末の操作で消した幕は稿ごと戻り、その操作でゴミ箱に入れた稿の件は消す。この端末で変えた、残る幕の採用・稿の一覧も採った側に戻る。稿の削除はそのまま）。採った側がこの端末なら、クラウドの幕を消す送信待ちを積み、まとまりとして送り直す。
  - 採らなかった側の稿は消さない。消える幕の稿と、残る幕に載らないこの端末の稿は、本文が採用原稿にそのまま入っていて推敲メモも空ならゴミ箱の1件「幕の分け方の競合で残した稿（n稿）」に、それ以外は残る幕・話の稿（採用しない）として残す。稿の幕が残っていればその幕に名前だけ変えて「第2稿（つないだ稿）（競合: iPhoneでの幕の操作）」、残っていなければ近くの幕へ移して「第2幕の第1稿（競合: iPhoneでの幕の操作）」（話を分けていなければ話、分けていれば元の並びで左隣の残る幕、なければ右隣。この端末で作った幕なら同じ位置の幕）。別の端末で作られた稿は「（競合: 別の端末での…）」（文書には端末の ID しか無いため）。
  - 片方の端末だけが幕の構成を変えていた時は、今までどおり1件ずつ合わせる。ただし話の採用稿は構成を変えた側（分けた時の採用稿）、幕の採用稿を両方が別々に変えていたら構成を変えた側（つないだ稿・分けた稿）にする（つないだ幕の本文が採用原稿から抜けないように）。もう一方の端末の書き換え・採用で採用原稿から外れたものは知らせ、消えた幕の稿なら残る幕・話の稿「第2幕の第1稿（競合: ○○での編集）」として残す（書き換え・採用した稿はいつも見える稿として残す）。
  - 削除が優先: 話が削除されていたら、もう一方の端末が分けた・つないだ幕も片付け、その稿はゴミ箱の1件「削除された話の幕の稿（n稿）」に残す（話をゴミ箱から戻してから戻すと、話・幕の稿として戻る）。この端末で消した幕・話の下に、後から届いた稿・幕も同じ（送信待ちの削除を送り直す）。
  - 別の端末のバックアップからの復元: 戻した話・幕の内容を正とする。この端末で分けた・さらに分けた・つないだまま送っていない幕と稿（クラウドに無いので、戻した端末は消さない）は、戻した話の幕の並び・幕の稿の一覧に載らないので、稿を控えて（残る幕・話の稿「（競合: ○○での幕の操作）」か、採用原稿にそのまま入っていればゴミ箱の1件）幕を片付け、「別の端末の分け方に合わせ…」と知らせる（載らない幕が残ると、修復が話に付け直して本文が重なるため）。幕の操作でなく、ふつうに足した・複製した稿は、名前を変えずに戻した話・幕の稿の一覧に載せ直す（幕の知らせは出さない）。戻したバックアップにその話が無い（話を作る前・削除した後のバックアップ、すべて削除）時は話が消えるので、この端末で送っていない幕の稿はゴミ箱の1件「削除された話の幕の稿（n稿）」に残して「…は別の端末で削除されていました」と知らせる（幕でない話の稿など、ほかの送っていない文章もゴミ箱に控える）。
  - この端末で別の稿を採用してから消した稿を、採った側の残る幕が採用していれば、その稿も戻す（幕に採用原稿が無くならないように）。
  - 分けた幕の第1稿・さらに分けた稿・つないだ稿・セパレート解除した稿（幕をつないだ稿）は、元の稿（`sourceVersionId`）と、その本文の指紋（`Version.sourceHash`）を控える（解除した稿は、分けた時の話の採用稿）。届いた幕の稿・解除した話の採用稿の元の稿が、この端末では書き換えられていたら（書き換える前の本文から分けた・つないだ・分けてから解除した）知らせる。同じ反映で別の端末から届いた元の稿の書き換えは比べない（解除より後の書き換えのことがある）。この端末で分けた話の、分ける前の採用稿の書き換えが届いた時も知らせる（話自身の稿に残っていて、幕には入っていない。同じ反映でその話のセパレートが解除された時は、解除した稿が採用原稿なので知らせない）。
  - 知らせは話ごとに1つ（ほかの競合の件数の前）。話はいまの番号で示す（この端末で削除した話は、そのゴミ箱の件の名前「第n話　題」。幕の稿のゴミ箱の件の「どの話か」も同じ）。「第3話　題の幕の分け方が別の端末と同時に変わりました。別の端末の分け方に合わせ、この端末での幕の操作は取り消しました（この端末で作った稿はゴミ箱に残しています）」「…この端末のセパレート解除を優先し、別の端末で分けた・つないだ幕の稿は稿の一覧に残しました」「第3話　題を削除したため、別の端末で同時に分けた・つないだ幕の稿はゴミ箱に残しました」「第3話　題は別の端末で削除されていました。…」「第3話　題の幕が別の端末で分けられた・つながれたため、この端末での編集・採用の一部が採用原稿に入っていません（稿の一覧に残しています）」「第3話　題の幕の操作と同時に別の端末で書き換えられた・採用された稿は、採用原稿に入れていません」「第3話　題の幕は、書き換えられる前の稿から分けられた・つながれたため、その書き換えが採用原稿に入っていません」「第3話　題の分ける前の採用稿が別の端末で書き換えられていました。…」。
  - 幕の稿のゴミ箱の件は、幕の属する話も控える（`TrashOrigin.parentId`。同期の競合でゴミ箱に入れた稿も）。
  - 決まりごと（受け入れている限り）: 同じ話の幕の構成を2台で同時に変えると、別々の幕の操作でも競合として扱う（先に送った端末の構成を採る。セパレート解除だけは優先）。負けた端末の、残る幕の採用の変更は取り消す（作った稿は残す）。まとまりが1回の上限を超えた時は途中の状態が一時的に見える。同じ端末の2つのタブで同時に幕の構成を変えた時と、クラウドの変更を反映している最中の画面の操作は、この規則の外（今までどおり項目ごと）。
- **共通の履歴が無い時**（初めてのログイン・アカウントの切り替え）: 端末内のレコードを「共通の履歴が無い」送信待ちにする。クラウドに何も無いものだけをそのまま送り、あるものは受信で突き合わせる。突き合わせではクラウド側を正とし、この端末にしか無い文章は控え（稿は別の稿、ほかはゴミ箱）、並びにはこの端末にしか無い要素を足す。クラウドで削除されていたものは削除を優先して控える。
- **バックアップからの復元・すべて削除**: 端末内を置き換え、すべてを「必ず上書き」の送信待ちにする。同期の時に、この端末に無いクラウドのレコードを消し（この端末が受け取っていなかったものも。消すものを決める全件の読み出しはサーバーから読み、途中でつながりが切れたら、端末の中の控えで決めずに、つながってからやり直す）、この端末の内容で上書きしてから受信を再開する。それまでクラウドの変更は反映しない。復元は、始めた時のクラウドの内容にだけ当てる: 初めて送る時に、クラウドの最後の書き込みの時刻（サーバーの時刻。削除の印も含めて新しい順に1件だけ読む）を記録し（`_meta` の `authoritativeFrom`。復元・初めてのログインのたびに決め直す）、それより後にほかの端末が書いたものは消さず、「必ず上書き」の送信待ちがあっても上書きせずに 3者マージする（base = 最後に知ったクラウド、この端末 = 戻した内容。ほかの端末の文章を採り、違う戻した文章は競合の控えになる）。消す・上書きするのは何回にも分かれ、途中でアプリを閉じる・止まる（iPhone で裏に回った・再読み込み）と、後で開いた時に続きから送るため。その間に復元の一部を受け取ったほかの端末が書いた・ゴミ箱に控えた文章を、続きで消さないように。クラウドのレコードを消す時は、送る時と同じく子（稿など）から先に消す（応募時の原稿の本文は応募計画の後）（何回かに分けて書いても、受け取った端末には、クラウドにあった子の削除が親の削除より先か同じ通知で届く）。ほかの端末は、復元で書かれた文書（`reset` の印。次に書かれるまで残る）の内容を正として当てる。消えた親の下に残っている子はその端末だけのもの（送っていない・書き換えたまま送っていない・復元の後に送った）なので、文章はゴミ箱に控える。ただし受け取った位置より後に書かれたものだけで、購読し直して受け取り済みの同じ時刻の文書が届き直した時は、ふつうの変更として3者マージする（その後にこの端末で分けた・書き換えた内容を戻さない）。
- **この端末が送った古い版**: 続けて送った時に、先に送った版の通知が後から届くことがある。送った版の指紋を覚えておき、もっと新しい版を送った後に届いた古い版は反映しない（巻き戻りと、自分自身との競合を防ぐ）。通知を受け取ってから反映するまでの間に送った時は、送る前のクラウドの版の通知が送った後に届くことがあるので、送った時に置き換えた版の更新時刻（サーバーの時刻）も覚えておき、その版とそれより前の版が届いても反映しない（後の版が届くまで。同期をやめて始め直した後も）。指紋（内容）では見分けない: 別の端末の削除（削除の指紋はどれも同じ）や、同じ内容で戻した書き込みを取りこぼさないように。同じ文書への後の書き込みは、どの端末のものでも時刻が必ず後になる。
- **データの形の版**（2.2。`src/sync/appModel.ts`）: クラウドの `users/{uid}/meta/app` に、データを書いたアプリの形の版（`model`。2.2 は 2）・アプリの版（`appVersion`）・時刻（`updatedAt`。サーバー時刻）を記録する。同期を始めるとこの文書を見張り、無い・この版より低ければこの版に上げる（下げない。アクセスルールでも下げられない）。この版より高ければ（新しい版のアプリが新しい形のデータを書いた）、受け取りは続けるが送るのは止め（この端末の変更は送信待ちに残る）、ヘッダーの同期の表示を「要更新」にし、画面の上に「新しいバージョンのアプリで保存されたデータがあります。アプリを更新してください」と「更新する」（新しい版が届いていれば切り替え、まだなら保存してから読み込み直す）を出す。記録が消えたら（新しい版をやめて戻した時に、コンソールで消す）この版を書き直して送るのを再開する。送っている途中で気付いた時も、次の書き込みからやめる。オフラインになったら（同期を続けたまま）、記録の見張りがサーバーと揃い直すまでは、送るトランザクションの中でこの記録も読んで確かめてから書く（オフラインの間に新しい版のアプリが記録を上げていることがある。見張りの「サーバーと揃った」通知は、online の知らせが無いまま回線が戻った時など、つながった後も Firestore の購読のつなぎ直しを待つ間（1分半ほどまで）届かないことがあるので待たない。読んだ記録は書き込みといっしょに確かめられ、書くまでに上げられたらやり直して読み直す。読み取りが増えるのは、この間に送るトランザクション1回につき1件だけ）。復元・すべて削除でまとめて消す前も、この間はサーバーから記録を読んで確かめる。オフラインになる前に始めた送信のトランザクションは、確かめずには書かない（次の回に確かめる）。同期を始めてから確かめるまで（同期を始めた直後の1回の読み取り）は送らない（いますぐ同期・ログアウトの前の送信は、確かめ終わるまで10秒まで待ってから送る。送れなければ「送信待ちの変更が n 件あります」と出す）。読めない・書けない時（アクセスルールを公開する前など）は止めない。持ち主ごとの文書なので、持ち主を変えると新しい持ち主の版から始まる。2.1 の端末はこの記録を知らないので止まらない（§6）。2.3 は 3（§7）、2.5 は 4（§11）、2.6 は 5（§13）。連携した Claude 用のコネクタもこの文書を読め、版が自分の版と違えば書き込まない。
- **持ち主**: 最初に同期を始めたアカウントをクラウドの持ち主として記録する（`config/owner`）。アクセスルールは持ち主の `users/{uid}/records` だけに読み書きを許し、文書の形と大きさも確かめる。同じ端末で以前と別のアカウントでログインした時は、同期を始める前に確かめる。
- **読み取りの量**: 初めての全件の受け取りが終わった時と、画面が20分以上裏にあった後・オフラインから戻った時は、記録した位置から購読し直す（長く切れていた購読は、始めた位置から全件を読み直すため）。
- **整合性の修復**: 修復（`repairData`）は画面に出す内容にだけ当て、端末内やクラウドには書き戻さない（利用者が触ったレコードだけを書く）。別の端末の変更は少しずつ届くので、途中の状態（話より先に稿が届いた等）を「直して」書き戻すと、後から届いたものと食い違うため。新しい版の端末が書いた知らない項目・値も、そのまま残る。
- **初回ログイン**: 端末内のレコードをすべて「クラウドに無い」前提で送信待ちにし、クラウドの全件を受け取る（ID が別なので両方残る。同じ ID のものは項目ごとに合わさる）。1.x の端末内データはこれでクラウドへ上がる。
- **ログアウト**: 端末内のデータと送信待ちは残す。同じアカウントでログインし直すと続きから同期する。
- **表示**: ヘッダーに同期の状態（同期済み・同期中・送信中・未送信 n 件（オフライン）・未ログイン・同期できません）を出す。「今すぐ同期」の後は、送り終えていれば「クラウドと同期しました」、送信待ちが残っていればその件数、初めての受け取り（新しい端末の最初のログインの直後など）がまだ終わっていなければ「クラウドの内容を受け取っています」と出す（最後に揃った時刻も、初めての受け取りが終わってから付ける）。ログインしたことのない端末では出さない（Firebase も読み込まない）。

## 5. 保存ボタン・巻き戻し・記号バー（2.1）

- **編集セッション**（`src/features/piece/session.ts`・`usePieceSession.ts`）: 原稿画面の本文・稿の名前・推敲メモ・話の題・特殊ブロックの見出しは、画面の中だけで「編集を始めた時の保存先の値（base）」と「いまの値」を持ち、「保存」（Ctrl/⌘+S）を押すまでストアに入れない（＝同期もしない）。ほかの画面は自動保存のまま。
- **保存時の競合**（`src/domain/pieceEdits.ts`）: 本文の保存先が base から変わっていたら（同期で別の端末の編集が届いた等）上書きせず、この端末の本文を同じ話の新しい稿「元の稿名（競合: この端末での編集）」として残して知らせる。稿の名前・推敲メモ・話の題・見出しはこの端末の編集を正とする。保存する前に稿が削除されていたら（別の端末で削除した等）、この端末の編集（本文・稿の名前・推敲メモ）を「元の稿名（競合: この端末での編集）」の新しい稿として残す。
- **離れる時の確認**: アプリ内の移動（リンク・パンくず・前後の話・ブラウザの戻る）は `useBlocker` で「保存して移動／保存せずに移動／キャンセル」を聞く（そのためルーターは `createHashRouter` のデータルーター）。同じ話の中で比較する稿を選び直す（`?v=` だけ変わる）時は聞かない。タブ・アプリを閉じる・再読み込みは `beforeunload`。採用・追加・複製・削除などの前と、アプリの更新（「更新する」）の前は「保存してから続けますか？」と聞く。確かめている間に「戻る」をもう一度押しても、確認は1つだけ出す。
- **端末内の控え**（`crashDraft.ts`）: 保存していない編集を `localStorage` の `novel-studio:edit:<話のID>` に、編集から1秒後（打ち続けていても3秒ごと）と、裏に回る・閉じる時に控える（同期しない）。次にその話を開いた時に「前回保存されなかった編集があります（日時）。復元しますか？」と聞き、保存・破棄したら消す。容量が足りない時は長い base を指紋だけにする。控えには書いた画面の印（owner）を入れ、その画面が開いている間は Web Locks のロック `novel-studio:edit-owner:<owner>` を持つ。同じ話を別のタブ・ウィンドウで開いた時、まだ開いているタブの控えは聞かず、消しもしない（保存・破棄で消すのも自分が書いた控えだけ）。
- **巻き戻し／進む**（`history.ts`）: 入力欄ごとに30手。1手は「位置・消した文字・入れた文字」の差分で持つ。続けて打った文字（・続けた削除）は1手にまとめ、1秒以上の間・改行・記号の挿入・カーソルの移動で区切る。日本語入力は確定した時に1手。記号バーのボタンと Ctrl/⌘+Z・Ctrl/⌘+Shift+Z・Ctrl+Y。戻したカーソル位置が見えるようにスクロールする。保存しても履歴は残る（破棄・競合した本文は消す）。
- **記号バー**（`SymbolBar.tsx`）: 巻き戻し・進む・ダッシュ（――）・三点リーダー（……）・全角空白・ルビ（選択あり: ｜選択《》、なし: ｜《》）・傍点（《《》》）。最後にフォーカスした本文・推敲メモに働き、押してもフォーカスを奪わない。原稿画面のいちばん下に常に置き、キーボードの変換候補のすぐ上に出す。iPhone の Safari・ホーム画面版は、キーボードに隠れる高さ（visualViewport で測る `--kb-inset`）だけ画面を詰める。iPhone のアプリ（2.4）は画面を縮めず（キーボードのプラグインの `resize: none`）、プラグインが知らせるキーボードの高さ `--kb-native` と visualViewport の大きい方だけ詰める（`src/platform/keyboard.ts`・`keyboardInset.ts`。二重に数えない）。iPhone のアプリの原稿画面では、キーボードの上の「完了」の帯を隠し、記号バーに「キーボードを閉じる」を出す。Android（ブラウザ・アプリ）は画面そのものが縮む。
- **話の一覧**（2.7。`src/features/piece/PieceJump.tsx`・`src/features/read/TocBody.tsx`）: 原稿画面の上部バーの「第n話」（特殊ブロックは見出しの前の「特殊」の札、幕に分けた話の画面は見出しの「第n話」）を押すと、そのタイトルのすべての話の一覧が開く。中身は通し読みの目次と同じ（章の区切り・特殊ブロック・幕に分けた話の下の幕・番号と題・採用原稿の無い話の「採用原稿なし」。題は保存した値。絞る欄はない）。今の話・幕に印を付け、開いた時にその位置を真ん中に出してフォーカスする。選ぶと一覧を閉じてから、その話・幕へ移る（保存していない編集があれば、前後の話への移動と同じ確認。キャンセルなら一覧は閉じたまま留まる）。今の話を選ぶと閉じるだけ。↑↓・Home・End で動き（端で止まる）、Enter で開き、Esc で閉じて押した所へ戻る。項目は本当の行き先のリンクなので、Ctrl・⌘ を押しながらで新しいタブに開ける。パソコンは押した所の下に開くポップオーバー（外側を押す・フォーカスが外へ出る・外側のスクロール・画面の幅の変更でも閉じる。推敲案の一覧より上に出す）、スマホ（幅 720px 以下）と高さ 500px 以下の画面は下からのシート（ダイアログ）。一覧は開いた時だけ作る（数百話でも開く・閉じるで止まらない）。通し読みの目次の動きは変えない（今の話の印も付けない）。
- **コピー**: 各ペインのコピーは「第3話　題」（題がなければ「第3話」。特殊ブロックは見出し）＋空行＋本文。保存していない編集も含めて表示している内容をコピーする。

## 6. セパレート（幕）（2.2）

- **データ**（`src/domain/types.ts`）: 幕は `Piece` の `kind: 'act'`。`parentId` に属する話、話の `actIds` に幕の並び（読む順）を持つ。幕は `title.structure`・`chapter.pieceIds` には載らない。第x幕の x は保存せず、`actIds` の中の位置から導出する（`actLabel`・`actNumber`。`src/domain/structure.ts`）。幕もほかの話と同じく稿・採用を持つ。下の「第n稿（分割）」「第n稿（つないだ稿）」「第n稿（幕をつないだ稿）」の n は、ほかの稿と同じく、その幕・話に今ある稿の名前のいちばん大きい番号＋1（ゴミ箱の稿は数えない。[SPEC.md](SPEC.md) の推敲バージョン。`src/domain/versionNumber.ts`）。`versionSeq` は古い版のアプリ・同期のために残すだけで、名前には使わない（確認文に出す名前も `nextVersionName` で作る稿と揃える）。
- **分ける**（`src/domain/acts.ts` の `separatePiece`）: 採用原稿のある第n話だけ。分割点（採用稿の本文の中の位置）で区切った本文が、各幕の「第1稿」（採用中）になる。区切るだけで本文は1字も変えない（各幕をつなぐと元の本文に戻る）。先頭・末尾・同じ位置・サロゲートペアや CRLF の途中は区切れない（`splitPointError`）。話自身の稿と採用はそのまま残るが、分けている間は変えられない（稿の追加・編集・削除・採用の変更は `DomainError`。採用を外す・変えようとすると「幕に分けた話の採用を変えるには、先にセパレートを解除してください」）。話の題は変えられる（各幕の見出しに入る）。
- **さらに分ける**: 幕の採用稿を区切り、その幕に最初の区切りの本文の新しい稿「第n稿（分割）」を作って採用し、残りの区切りの幕（第1稿）をすぐ後ろに入れる。その幕のほかの稿は残る。
- **次の幕とつなぐ**（`joinActWithNext`）: 両方の幕に採用稿がある時だけ。この幕に「第n稿（つないだ稿）」（この幕の採用稿＋次の幕の採用稿）を作って採用し、次の幕を消す。次の幕の採用していなかった稿は「第3幕の第2稿」のような名前でゴミ箱へ（1件）。戻すと、つないだ先の幕の稿として戻る（`TrashOrigin.pieceId`）。消える幕の採用稿の推敲メモは、「【第2幕　第1稿】」のような見出しを付けて、つないだ稿の推敲メモに引き継ぐ（解除でも同じ）。
- **セパレート解除**（`unseparatePiece`）: すべての幕に採用稿がある時だけ（なければ「第2幕に採用原稿がないため、セパレートを解除できません」）。各幕の採用稿をつないだ本文を話の新しい稿「第n稿（幕をつないだ稿）」として採用し、幕と幕の採用稿を消す。各幕の採用していなかった稿はゴミ箱へ（操作全体で1件。戻すと話の稿として戻る。話をまた幕に分けていれば戻せない）。
- **消えた幕の稿をゴミ箱から戻す**: 幕の稿のゴミ箱の件（幕から削除した稿・つないだ時の残り）は、幕の属する話も控える（`TrashOrigin.parentId`）。つないだ・解除した時は、消える幕を戻し先にしていた件を、残る幕・話へ付け替える。戻す先は、稿の幕・話 → 控えた場所（`origin.pieceId`）→ 幕の属していた話（まだ分けていれば第1幕。つなぐと前の幕が本文を引き継ぐので、第1幕はいつも残っている）の順に探す。元の幕から移して戻す稿は採用しない（つないだ本文の採用稿が黙って入れ替わらないように）。
- **話の本文**: 分けている間、上位の層（文字数・タイトルや章の集計・進捗・通し読み・各話テキスト書き出し・応募時の記録・ホームのタイトルの集計）に反映される本文は、各幕の採用稿を読む順につないだもの（`adoptedText`。幕と採用稿が変わらない限り同じオブジェクトなので、文字数のキャッシュが効く）。採用稿のない幕は何も足さず、「採用原稿なし 1幕」として数える。通し読み・全文の書き出しでは幕の見出し（第1幕…）の下に各幕を出し、採用稿のない幕には「採用原稿がありません。」。各話テキスト書き出しは1話1ファイルで、各幕の前に幕の見出しを入れる（採用稿のない幕は飛ばし、書き出す前に知らせる）。応募時の記録の稿の印は話自身の（分けた時の）採用稿なので、分けただけでは「稿が変わった」にならない。
- **削除・並べ替え**: 幕に分けた話も、削除できるのは採番スコープの最後の話だけ。話・幕・すべての稿を1件にまとめてゴミ箱へ移し、戻すとすべて元どおり（同じ id が残っていて複製として戻す時も、幕の参照を付け替える）。並べ替えても幕はそのまま付いていく。幕だけを削除・並べ替えることはできない。
- **整合性の修復**（表示用。書き戻さない）: 属する話（同じタイトルの第n話）のない幕は見えなくする。話の `actIds` は、ある幕でその話を指しているものだけにする。話を指しているのに載っていない幕は、保存されている `actIds` が空でない時と、`actIds` が無い（一度も分けていない話に、分けた端末の話の更新より先に幕が届いた）時だけ、作られた順（同じ時刻なら id の順）に後ろへ足す。`actIds` が空（`[]`。セパレートを解除した話）なら足さない（解除した端末の幕の削除が届くまでの間や、解除と別の端末での幕の変更が重なった時に、採用稿のない幕・一部の幕だけの話に見えないように。残った幕は見えないまま、話の削除でいっしょに片付く）。分けた時の幕の作った時刻は読む順に1ずつずらす。第n話以外の `actIds` は使わない。幕の `kind` は幕のまま。`parentId` を持つ話（古い版の端末が幕を第n話として書き戻したもの）も幕として扱う（本編の並びに入れない）。
- **同期**（`src/sync/acts.ts`・`src/sync/batch.ts`・`src/db/persistence.ts`。詳しくは §3 の「幕のまとまりの送信」「幕の構成の競合」）: 幕の構成を変えた話は、話・幕・稿・その操作のゴミ箱の件を1つのトランザクションで送る（ほかの端末は途中の状態を見ない）。別々の端末で同じ話の幕の構成（分ける・さらに分ける・つなぐ・解除）を同時に変えたら、話を1つのまとまりとして、どちらかの構成を丸ごと採る（セパレート解除を優先し、それ以外は先に送った端末）。負けた側の幕・稿は、残る幕・話の「（競合: ○○での幕の操作）」の稿かゴミ箱に残し、その話の名前で知らせる（本文が重複したり一部が抜けたりしない）。片方だけが構成を変えていた時は1件ずつ合わせ、構成を変えた側の採用稿を採る。話が削除されていれば幕も片付け、もう一方の端末が作った幕の稿はゴミ箱の1件に残す。
- **古い版（2.1）の端末**: 幕を知らないので、幕がふつうの第n話として本編の末尾に並び（話数・文字数がずれる）、最後の幕を「最後の話」として削除できてしまう。2.2 の端末では、そうして削除された幕（`kind: 'episode'` で `parentId` を持つ話のゴミ箱の件）を戻すと幕として戻す（話をまた分けていなければ戻せない）。同期している端末で初めて分ける時に、ほかの端末のアプリを先に新しくするよう一度だけ案内する（強制はしない）。2.2 からはクラウドにデータの形の版を記録し（§3「データの形の版」）、2.2 以降のアプリは、自分より新しい版で書かれたデータがあると送るのを止める。2.1 のアプリはこの記録を知らないので、この仕組みでは止まらない（案内だけが頼り）。
- **画面**:

## 7. 推敲案・改稿案・作品批評と Claude 連携（2.3）

- **データ**（`src/domain/types.ts`）: 6つの表を足す（Dexie v4。どれもタイトルの配下の1レコード = 1文書で、並びはタイトルの側に持たず `order` か日時で並べる）。共通の項目は `v`（記録の形の版。いまは 1。これより新しい版は「新しいコネクタの記録」）・`source`（`claude` = コネクタ、`paste` = 手動連携の貼り付け、`manual` = アプリで手で書いた）・`titleId`・`createdAt`・`updatedAt`。

## 8. iPhone・Android のアプリ（2.4）

- **形**（`capacitor.config.ts`）: Capacitor 8.5.3。画面は Web 版と同じコードで、`npm run build:native`（`vite build --mode native`）がサービスワーカーを入れずに `dist-native` に出したものをアプリに載せる。`ios/`・`android/` はリポジトリに入れ、署名の鍵・Firebase の設定ファイル・`ios/App/local.xcconfig` は手元だけに置く（`.gitignore`。リポジトリは公開）。画面の origin は iPhone `capacitor://localhost`・Android `https://localhost`（端末内のデータの置き場所が決まるので、一度入れたら変えない）。
- **アプリかどうか**（`src/platform/platform.ts`）: `Capacitor.getPlatform()` が `ios`・`android` の時だけアプリの動きにする（Web 版は今までどおり）。アプリだけの部品は `src/platform/` に置き、重いもの（ログインのプラグイン・Filesystem）は使う時に読み込む。

- **キーボードと記号バー**: §5。
- **ファイルの保存**（`src/platform/saveFile.ts`）: WebView のダウンロードは何もしないので、端末の一時置き場（Cache）に書いてから、アプリに入れた `SaveAs` プラグインで保存先を選んでもらう（iPhone `ios/App/App/SaveAsPlugin.swift` =「ファイル」の書き出しの画面、Android `android/app/src/main/java/jp/barraquda/novelstudio/SaveAsPlugin.java` =「保存」の画面）。やめたら何もしない（バックアップの書き出しの日付は保存した時だけ変える）。保存の途中にもう一度押された時も何もしない（一時置き場を1つ使い回すので、重ねて保存しない）。一時置き場の名前は 240 バイト（UTF-8）までに縮める（Android は名前が 255 バイトまで。保存先の名前は元のまま渡す）。各話の書き出しはアプリでは ZIP（フォルダを選ぶ書き出しは Web 版だけ）。

- **Android のバックアップ**: `allowBackup="false"` と `data_extraction_rules.xml` で、Google のバックアップ・機種変更の引き継ぎに端末内のデータを写さない（写すと端末の ID が同じになり、同期が自分の書き込みを見分けられなくなる）。新しい端末ではログインしてクラウドから受け取る。

## 9. 応募計画の規定の備考・提出する梗概／キャッチコピー・特記事項

- **項目**（`Submission`。後から足した項目で、古いデータには無い。無ければ空・規定なしとして扱い、修復でも補ったことにしない）: 規定の備考 `limitNote`（ルビ不可・章タイトル必須など、コンテストごとの注意点）、提出する梗概・あらすじ `synopsis` と文字数の規定 `synopsisMin`・`synopsisMax`、キャッチコピー `catchphrase` と `catchphraseMin`・`catchphraseMax`（規定は字数。未設定は null）、特記事項 `specialNotes`（自由に書く欄）。新しく作る応募計画（［応募計画にする］も）は空・null で作る。
- **画面**（`src/features/title/strategy/SubmissionCard.tsx`）: 規定の欄の文字数の下に「規定の備考」。コンテストの概要の下に「提出する梗概・あらすじ」「キャッチコピー」（本文・下限〜上限（原稿の規定と同じ読み方: 10万・全角数字など。Enter・フォーカスを外した時に保存）・入力中の文字数「330字（空白・改行を除く） → 30字超えています」）、その下に「特記事項」。文字数は原稿と同じ数え方（`countChars`: 空白・改行、ルビ・傍点の記号とルビの読みを除く）。判定と言い方は `src/domain/submissionTexts.ts`（あと…字・…字超えています・規定内）。畳んだカードには、応募前で規定を外れている時だけ「梗概 +12字」「キャッチコピー あと5字」の札を出す。
- **応募時の記録**: 応募時の原稿を記録する時、その時の梗概・あらすじとキャッチコピーも `snapshot.synopsis`・`snapshot.catchphrase` に控え、記録の欄に「提出した梗概・あらすじ（…字）」として読むだけで出す（長い梗概は畳む）。古い記録には無いので何も出さない。
- **同期**: 規定の備考・梗概・あらすじ・特記事項は長い文章（`TEXT_FIELDS`。両方で変わればつなぐ）、キャッチコピーと文字数の規定は短い項目（両方で変えたらこの端末）。足した項目だけなので `DATA_MODEL` は上げない。古い版の端末も知らない項目をレコードごと受け取って端末内に持ち、書き換えても消さない: 3者マージは自分が変えた項目だけを重ねる（`mergeFields` は相手の内容から始め、この端末と base にある項目だけを見る）。修復が表示用の内容から外す項目（2.4 までの修復は応募時の記録を知っている項目だけで作り直すので、記録の中の `synopsis`・`catchphrase`）も、そのレコードを書き換えて保存する時は、表示用の内容と端末内の内容が違うので端末内の内容に3者マージで重ね（`persistence.save`）、外した項目は端末内の内容のまま残る（`src/store/appStore.test.ts`）。この版の修復は控えも残す。古い版（2.4 まで）の端末では、規定の備考・梗概・キャッチコピー・特記事項などの応募計画そのものの項目はどの操作でも残るが、応募時の記録の中の控え（`snapshot.synopsis`・`snapshot.catchphrase`）が残るのは、書き換えて保存する時だけ。その端末で応募計画やタイトルを削除する（ゴミ箱の写しは表示用の内容から作る）、バックアップを書き出す（表示用の内容を書き出す）、バックアップから復元する（修復した内容で端末内もクラウドも置き換える）と控えが消え、新しい版の端末で戻しても「提出した梗概・あらすじ」「キャッチコピー」は出ない。その端末で記録し直すと控えのない記録になる。控えを頼りにするなら、先にすべての端末を新しい版にする（消える仕組みも `src/store/appStore.test.ts`）。
- **Claude 連携**: `novel_get_strategy` の一覧には、規定の備考・梗概（文字数と規定の判定）・キャッチコピー（同じく。中身も）・特記事項の抜粋を、1つを全文で読む時（`submission_id`）は各項目の全文と文字数・規定の判定を出す（書いていない項目は出さない）。手動連携の戦略の依頼文の応募計画にも同じ抜粋を入れる（`submissionExtraLines`）。

## 11. 相対比較（2.5）

- **要件**: 個人的に購入した既存の作品の PDF を Claude に多角的に分析してもらい、その分析を Novel Studio に置いておく。PDF は claude.ai の
  プロジェクトのナレッジに置いたまま（Firebase の Spark プランにはファイルの置き場所が無い）、分析だけを残す。決めたこと: (1) ホームの独立した棚
  （すべてのタイトルで共有）で、各タイトルは棚から相対比較する作品を選ぶ、(2) 1つの作品に分析はいくつでも（観点の名前・Markdown の本文・日付。
  観点は Claude が決めてよい）、(3) Claude（コネクタ）が分析を書き、作品批評の時に読む（PDF を毎回渡さなくてよい）、(4) 名前は「相対比較」（棚の1つ1つは「作品」）。コード・データ・ルート（`/bench/:workId`）・`data-testid`・コネクタのツールの名前と JSON の項目は

## 12. 縦書きのページ表示（通し読み）

- **要件**: 通し読みの縦書きで、一太郎で組んだ時のように、タイトルごとに決めた字数×行数のページに分けて読む（ページ数の見積もり。
  一太郎とぴったり同じにはならない）。横書きは今までどおり。
- **データ**（`src/domain/types.ts`・`src/domain/pageSetup.ts`）: `Title.pageSetup`（`{ chars, lines }` = 1行の字数・1ページの行数）。
  無い = 40字×32行（`DEFAULT_PAGE_SETUP`）。選べるのは 20×20・40×30・40×32・40×40・42×34（`PAGE_SETUP_PRESETS`）と、自由に入れた値
  （字数 10〜60・行数 5〜60 の整数。全角の数字も読む。`checkPageSetup`・「40×32」の1つの欄なら `parsePageSetup`。範囲の外は
  「1行の字数は 10〜60 の数で入れてください」「1ページの行数は 5〜60 の数で入れてください」）。読む時は `pageSetupOf(title)`
  （無い・範囲の外・壊れた値は既定）。操作は `setTitlePageSetup`（`src/domain/entityOps.ts`・`actions.setTitlePageSetup`。null で既定に
  戻す = 項目を消す。既定と同じ値を選んだ時も決めた値として残す。範囲の外は DomainError。同じ値なら何もしない）。
- **同期**: 短い項目。2つの値をまとめて1つの項目として合わせる（両方で変えたらこの端末。字数だけ・行数だけが混ざって、どちらの端末も
  選んでいない組み合わせにならないように）。足しただけの任意の項目なので `DATA_MODEL` は上げない（古い版の端末も知らない項目として
  レコードごと持ち、書き換えても消さない。§9 と同じ）。記録の中身は JSON の文字列なのでアクセスルールも変えない。修復は書き換えない
  （範囲の外・壊れた値も残し、読む時に既定として扱う。新しい版で範囲を広げても、古い版の端末で消えないように）。バックアップにもそのまま入る。
- **組み方**（`src/features/read/verticalPages.ts`。純粋な計算で、画面を持たない）:
  - 話（第n話・特殊ブロック）ごとに新しいページから始める。話の頭に見出しの行「第n話　題」（通し読みと同じ表記。題が無ければ「第n話」、
    特殊ブロックは見出し名）と空行1行。見出しは記法として読まず、長ければ折り返す。
  - 幕に分けた話は、幕の境目でページを変えない。幕の見出し（「第1幕」）を1行に置き、続けて幕の本文。採用稿のない話・幕は
    「採用原稿がありません。」の1行。章の見出しはページに入れない（画面がページの外に出す）。ページの番号は、通し読みの範囲
    （タイトル全体か章）の最初の話を1とする。
  - 段落（本文の改行）ごとに新しい行。空行も1行。字下げは書いたとおり（自動で下げない。折り返した行も下げない）。話の末尾の空行は
    数えない（白紙のページを作らないため）。
  - マス: 全角は1マス、半角の英数字・記号・空白と半角カナは 0.5 マス（本文は縦中横にしない。話・幕の見出しの2桁までの半角数字は、
    画面が縦中横にするので分けない1マス（「第1話」は3マス）。3桁以上は半角のまま数え、行では分けない）。「――」「……」は書いたとおり1字1マス。
    ルビ・傍点の記法は親文字だけをマスに数え、記法は行の文字に残す（画面はルビを小さく出せる）。異体字セレクタ・結合文字は幅 0。
  - 禁則: 行頭に来る「、」「。」「，」「．」（半角の「､」「｡」も）は前の行の最後のマスの外へぶら下げる（1行に1字）。行頭に来る閉じ括弧
    （」』）】〉》］｝〕〗〙〟’” と半角の ) ] }）・「？」「！」（全角・半角、‼⁉ も）・「ー」は前の行の末尾に追い込む（その行は字数を超える。
    字数を超える分はぶら下げと合わせて3マスまでで、それより多い分は次の行の頭に置く）。行末の禁則（開き括弧を行末に置かない）・
    分離禁止（「……」「――」を行で分けない）はしない。

    傍点は1字ずつ分けられ、行ごとに《《…》》で閉じ直す。

    最初のページの番号、ページ数、幕の見出しのページと行。全体のページ数。話ごとの覚え（`createPageCache`）があると、本文・見出し・
    字数が変わらない話は組み直さず、同じページの配列を返す（行数だけを変えた時はページに分け直すだけ）。80万字で数十ミリ秒
    （すべての段落にルビ・傍点があっても百ミリ秒ほど）。

  （横書きは今までどおり）。

    地 4.25マス。行の末尾に3マスまで追い込んだ字とも重ならない）。1字は1マス（続く全角の約物「。」」も詰めない。`text-spacing-trim`）。

    開いている間（幅 1100px 未満で高さ 500px を超える画面）は、枠が低くなってもページを縮めない（閉じれば同じ大きさ・同じ所）。目次を本文の

  - `novel_get_material`「資料を読む」: 資料（`d:…`・id・資料名）の記録を項目ごとに。`sections` で絞る、`note_id`（`k:…`）で1つだけ。長ければ
    `char_budget` 字ずつ（相対比較の分析を読む時と同じ既定）、続きは cursor（項目の絞り込みも続く）。
  - `novel_add_material_notes`「資料に記録を追加」（作るだけ）: `{ material, new_material?: { name, author, publisher?, year?, pdf_place? },
    items[≤20]: { section, body_markdown, run_date? }, model? }`。**タグは無い**（`new_material` に `tags`・`field` などが付いていても資料には入れない）。
    決まりは相対比較の `novel_add_bench_analysis` と同じ: 資料は `material` → `new_material.name` の順に探し（`refKey`）、資料名で見つけた資料の著者と
    `new_material` の著者が両方あって違えば別の資料（「著者の違う同名の資料 d:…『…』（…） があるため、別の資料として足しました」）、資料の棚に無ければ
    `new_material` がある時だけ、記録を1つでも作る時だけ作る（作った時は「資料 d:…『…』（…） を資料に追加しました」）。削除した資料は、ゴミ箱に
    同じ資料名の資料がある間は作り直さない（`trashedMaterialNamesOf`。「資料『…』は以前に削除されています（ゴミ箱にあります。…）」）。ゴミ箱から
    完全に削除した後は、相対比較の作品と同じく通し番号を足した id（`materialId(name, author, 2)`…）で新しい資料として作り直す。記録は2回送っても1つ（削除したものは
    「以前に削除」）。1件が JSON にして 200,000 字を超える時は、番号を付けて分ける分け方を返す。答えには足す先の資料をいつも `d:…` で出す（既にある
    資料に足した時は「資料 d:…『…』（…） に追加しました」、何も足さなかった時は「資料 d:…『…』（…） には何も追加していません」。資料の棚に無い資料で
    記録を1つも作れなかった時は資料も作らず「記録を1つも追加しなかったため、資料『…』（…）は資料の棚に追加していません」）。説明には、決まった4つの
    項目ごとの書き方（要約は資料の全体の要約（章立てに沿って）、創作に役立つ知識・描写に使える部分は資料の中から**すべて**拾い出どころを添える、
    サンプルシーンは拾った知識と描写で仮想の場面を1つ立ち上げ、設定を1〜2行で示してから数百〜2,000字ほど）、長い時は項目ごとに分けて送ること、
    「タグは作者が自分で付けて管理する（Claude はタグを付けない）」を書く（`MATERIAL_SECTION_GUIDE`。手動連携の依頼文と同じ）。
  - サーバーの説明に資料の一文（作者が「参考資料」「資料本」とも呼ぶ・設定や描写を考える時に `novel_get_material` で読める）と短い id（`d:`・`k:`）を
    足し、見える範囲に資料を足した（全体で 900 字未満のまま）。
- **手動連携**（`src/claude/prompts.ts`・`paste.ts`）: 資料の画面の「Claude に頼む（手動）」は、選んだ項目（既定は決まった4つ）で資料の PDF を読んで
  記録してもらう依頼文（`materialNotesPrompt`。「このプロジェクトのナレッジにある資料『…』（著者）の PDF を読んで、小説の書き手が創作に使うための
  記録を書いてください。」・PDF の置き場所・項目ごとの書き方・すべて拾うこと・PDF に無いことは推測で書かないこと。PDF はプロジェクトにあるので本文は
  送らない。最後に `novel_add_material_notes` と同じ形の JSON をコードブロックで返してもらう）。依頼文はタグに触れない。「結果を貼り付け」はその資料の
  記録として受け付ける（`materialId`。`material`・`new_material` は使わない。ほかのツールは受け付けない。資料は数えない）。
